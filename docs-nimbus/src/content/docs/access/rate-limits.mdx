Rate limits cap how much traffic a key, user, team, or the whole gateway can send. They apply to inference requests, Anthropic token counts, and MCP tool calls. They are separate from [budgets](https://docs.oceans-llm.com/access/budgets): budgets cap spend, and rate limits cap volume.

The design and its trade-offs are in the [ADR on gateway rate limits and request quotas](https://github.com/ahstn/oceans-llm/blob/main/docs/adr/2026-10-15-gateway-rate-limits-and-quotas.md).

## Policies

A policy counts one kind of traffic for one scope over one window. Policies come from two places:

- Config policies in `gateway.yaml` set platform-wide defaults. See [YAML fields](#yaml-fields).
- Admin policies are managed by platform admins in the admin UI or the admin API. See [Manage policies in the admin UI](#manage-policies-in-the-admin-ui).

| Field | Values | Notes |
|---|---|---|
| `operation` | `inference`, `count_tokens`, `mcp_tool_call` | See [Operations](#operations). |
| `scope` | `global`, `api_key`, `user`, `team` | See [Scopes](#scopes). |
| `model` | gateway model key | Optional. Only for `inference` and `count_tokens`. |
| `mcp_server` | MCP server key | Optional. Only for `mcp_tool_call`. |
| `metric` | `requests` (default), `tokens` | `tokens` is valid only with `inference`. |
| `period` | `minute`, `hour`, `day`, `month` | See [Windows](#windows). |
| `limit` | positive integer | |

### Operations

- `inference` covers `/v1/chat/completions`, `/v1/responses`, `/v1/messages`, `/v1/embeddings`, `/v1/images`, `/v1/images/generations`, `/v1/decisions`, and `/v1/systemone`. It also covers the unversioned aliases (`/chat/completions`, `/responses`, `/messages`, `/embeddings`, `/images`, `/images/generations`, `/decisions`). `/v1/systemone` has no unversioned alias.
- `count_tokens` covers `/v1/messages/count_tokens` and `/messages/count_tokens`.
- `mcp_tool_call` covers `tools/call` on `/mcp/<server_key>` and the aggregate `call_tool` on `/mcp`. It also covers the resources, prompts, and completion methods on `/mcp/<server_key>`, because they read server data through the same upstream access. All of these share one counter per policy. The aggregate `search_tools` and `describe_tool` read the gateway's own catalog and call no MCP server, so they are not counted.

### Model and MCP server filters

A `model` filter matches the requested model or the model it resolves to. A policy on a model therefore also covers its aliases. Without a `model` filter, an inference or token-count policy matches every model.

An `mcp_server` filter matches calls to that one MCP server. Without it, an `mcp_tool_call` policy matches calls to every server. Model filters and MCP server filters can't be combined: `model` is rejected on `mcp_tool_call` policies, and `mcp_server` is rejected on the other operations.

### Scopes

- `global` is one counter for all traffic the policy matches.
- `api_key` gives each credential its own counter. For an MCP client that signed in with OAuth, the credential is its grant, so each authorised client has its own counter.
- `user` gives each user their own counter across all their keys and OAuth clients. It applies to user keys and OAuth callers. A service-account key has no user, so `user` policies don't match it.
- `team` gives each team its own counter. It applies to a service-account key's team, and to a user who belongs to a team, whether they use their own key or an OAuth client. Every member counts against the team's counter.

Config policies always give each principal its own counter. Admin policies can also target one specific key, user, or team.

The gateway reads a user's team only when a team policy could apply, and caches it for `policy_refresh_seconds` (10 seconds by default). If that read fails, `failure_mode: closed` rejects the request with `503`, and `open` checks the other policies.

### Every matching policy applies

The gateway checks a request against every enabled policy that matches it, and the most restrictive one wins. If any matching policy is exhausted, the gateway rejects the request and charges nothing against the other policies.

A specific policy can tighten a default for one principal, but it can't raise it. For example, a config default of 600 requests a minute per key and an admin policy of 60 a minute for one key leave that key at 60. Every other key stays at 600.

### Windows

- `minute` and `hour` are sliding windows. The gateway estimates usage over the last 60 seconds or the last hour from the current and previous fixed windows. It weights the previous window by how much of it still overlaps. This avoids the double burst that a fixed window allows at its boundary.
- `day` and `month` are quotas on UTC calendar windows. They reset at 00:00 UTC each day and on the first day of each month.

### Token limits

Token counts are known only when a response finishes. A `tokens` policy rejects a request when its window is already used up. After the response completes, the gateway charges the response's `total_tokens`. The charge is written before the response is returned, so requests sent one after another always see earlier usage. Concurrent requests can each pass the check before the others are charged, so a token limit can be exceeded by up to one response per request in flight.

Token limits count the usage the provider reports, which is the same usage budgets charge. That includes partial usage from a failed request, from a stream that ended in an error, and from a stream the client cancelled after usage was reported, because the provider consumed those tokens. A response's usage is charged to all of its token policies or to none.

A cancelled stream is charged in the background. The next check of the same token counter on that gateway instance waits up to one second for the charge, so a client that cancels and retries straight away still sees the usage. In `closed` mode, a check that is still waiting after that second is rejected with `503`.

Requests that report no usage are not charged. Batch jobs are not charged.

## Responses

When a policy is exhausted, the gateway returns `429`. The check runs after the gateway resolves the requested model, and before guardrails, budget checks, and any provider or upstream MCP call.

OpenAI-compatible routes return:

```json
{"error": {"type": "rate_limit_error", "code": "rate_limited", "message": "..."}}
```

`/v1/messages` and `/v1/messages/count_tokens` return the Anthropic error shape:

```json
{"type": "error", "error": {"type": "rate_limit_error", "code": "rate_limited", "message": "..."}}
```

MCP methods counted by `mcp_tool_call` return a JSON-RPC error with code `-32029` and this `data`:

```json
{"error_code": "rate_limited", "retry_after_seconds": 12}
```

For a JSON-RPC notification, the error has no `id`.

The message names the scope kind, the limit, the window, and the retry delay. For example: `rate limited: API key rate limit exceeded: 60 inference requests per minute. Retry after 12 seconds`. The JSON-RPC error message has no `rate limited: ` prefix. Messages never include ids.

### Headers

The gateway sends rate-limit headers only on requests that at least one policy matched. Requests that no policy matches carry none of them.

| Header | Sent on | Value |
|---|---|---|
| `Retry-After` | rejected requests only | Seconds until the request would fit. |
| `X-RateLimit-Limit` | matched requests | The tightest policy's limit. |
| `X-RateLimit-Remaining` | matched requests | Requests or tokens left in that policy's window. |
| `X-RateLimit-Reset` | matched requests | Seconds until that policy's whole limit is free again. |

For `day` and `month`, `X-RateLimit-Reset` is the end of the window. For `minute` and `hour`, usage in the current window keeps counting, at a falling weight, until the end of the next window, so the reset is the end of the next window. This is why `Retry-After` (when one more request fits) is often shorter than `X-RateLimit-Reset`.

The tightest policy is the one that rejected the request. When the request was admitted, it's the policy with the smallest share of its limit left. The gateway compares shares rather than amounts because request limits and token limits count different units.

The headers describe the state when the request was admitted. For a token policy, `X-RateLimit-Remaining` doesn't include the tokens of the response that carries it, because streamed responses send headers before usage is known. Non-streaming responses behave the same way, so the two agree. The next request's headers include those tokens.

When the counter store fails in `open` mode, the gateway admits the request without rate-limit headers.

### Retries and fallbacks

- The gateway checks a request once, before any provider attempt. Provider retries and fallbacks inside the gateway are not counted again.
- A client retry is a new request, so it's counted again. The OpenAI and Anthropic Python SDKs retry `429` with backoff by default and read `Retry-After`.
- Budget rejections use `422` by default, so `429` from this gateway normally means "slow down". If `budgets.exceeded_status_code` is set to `429`, a `429` can also be a budget rejection. Check `error.code`: it's `rate_limited` for a rate limit and `budget_exceeded` for a budget. See [hard and soft limits](https://docs.oceans-llm.com/access/budgets#hard-and-soft-limits).
- Each key can have at most 8 token counts in flight on each gateway instance. The gateway checks that cap before rate limits, and it also returns `429`.

## Storage and replicas

Counters live in the gateway database (`rate_limit_counters` table), so every replica enforces the same limits. No Redis or other store is needed. Each check is one short transaction that charges every matching counter only if all of them admit the request. In Postgres, the charge locks the counter row until the transaction commits, which serialises concurrent checks of the same counter across replicas.

When no policy matches a request, the check makes no database call.

Counter rows expire one window after their window ends. Each replica deletes expired rows at most once a minute, in batches of 500 until a batch comes back short, up to 50,000 rows a minute. The cleanup runs on any checked request while policies are loaded, whether or not a policy matches it.

### When the database fails

`rate_limits.failure_mode` controls what happens when a counter check fails:

- `open` (default): the gateway admits the request without rate-limit headers and logs a warning.
- `closed`: the gateway rejects the request with `503`. MCP methods counted by `mcp_tool_call` return HTTP `503` with a JSON-RPC error (code `-32603`). After a token usage write fails, requests that match a token policy are also rejected for 5 seconds, so usage that couldn't be recorded can't keep passing a read-only check.

Both modes treat a replica that has never loaded the admin policies, and can't, as a store failure, because it can't tell which policies a request would match. A replica that loaded them before keeps enforcing that set.

API-key authentication uses the same database, so most requests fail anyway when it's down. Failing open keeps a counter-only problem, such as lock contention, from becoming an outage.

## YAML fields

`rate_limits` in `gateway.yaml` sets platform-wide default policies and how enforcement behaves. The whole section is optional. Without it, no config policies exist, `failure_mode` is `open`, and `policy_refresh_seconds` is `10`.

```yaml title="gateway.yaml"
rate_limits:
  failure_mode: open          # or closed
  policy_refresh_seconds: 10  # 1 to 3600
  policies:
    - name: inference per key
      operation: inference
      scope: api_key
      period: minute
      limit: 600
    - name: tokens per team
      operation: inference
      scope: team
      model: fable-5
      metric: tokens
      period: hour
      limit: 5000000
    - name: token counts per key
      operation: count_tokens
      scope: api_key
      period: minute
      limit: 300
    - name: notes calls per key
      operation: mcp_tool_call
      scope: api_key
      mcp_server: notes
      period: day
      limit: 5000
```

| Field | Default | Notes |
|---|---|---|
| `failure_mode` | `open` | `open` admits requests when the counter store fails. `closed` rejects them with `503`. |
| `policy_refresh_seconds` | `10` | How often each replica reloads admin policies. `1` to `3600`. |
| `policies` | `[]` | List of config policies. |
| `policies[].name` | required | Unique, 1 to 100 characters after trimming. |
| `policies[].operation` | required | `inference`, `count_tokens`, or `mcp_tool_call`. |
| `policies[].scope` | required | `global`, `api_key`, `user`, or `team`. |
| `policies[].model` | none | Gateway model key. `inference` and `count_tokens` only. |
| `policies[].mcp_server` | none | MCP server key. `mcp_tool_call` only. |
| `policies[].metric` | `requests` | `requests` or `tokens`. `tokens` needs `operation: inference`. |
| `policies[].period` | required | `minute` or `hour` (sliding), `day` or `month` (UTC calendar quotas). |
| `policies[].limit` | required | Integer greater than `0`. |

### Validation

The gateway refuses to start when:

- the section has unknown fields, or an unknown operation, scope, metric, period, or failure mode
- `limit` is `0` or less, or a name is empty, longer than 100 characters, or not unique after trimming
- `policy_refresh_seconds` is outside `1` to `3600`
- `metric: tokens` is set on an operation other than `inference`
- `model` is set on `mcp_tool_call`, or doesn't name a configured gateway model
- `mcp_server` is set on an operation other than `mcp_tool_call`
- an operation has more than 100 enabled policies, counting config policies and enabled admin policies together
- a config policy has the same name as an admin policy, whether the admin policy is paused or not

Config policies can't name a specific key, user, or team. A policy whose `mcp_server` isn't registered logs a warning at startup and applies once a server with that key exists.

The 100-policy cap per operation bounds the work one request can cause, because every request is checked against all enabled policies for its operation.

### Recommended starting points

Start with generous per-key limits that only stop runaway clients. Then tighten them for specific keys or teams.

| Traffic | Suggested starting point |
|---|---|
| Inference requests | 600 per minute per key |
| Inference tokens | A per-user or per-team hourly token limit sized to your provider quota |
| Token counts | 300 per minute per key |
| MCP tool calls | 120 per minute per key, plus a daily quota on servers with costly or rate-limited upstreams |

A `global` policy protects a shared provider quota, but it serialises every matching request on one counter row. For high-volume traffic, prefer per-key or per-team policies.

## Manage policies in the admin UI

Platform admins manage admin policies on the **Rate Limits** page of the admin UI, or through the admin API:

- `GET /api/v1/admin/rate-limits` lists policies.
- `POST /api/v1/admin/rate-limits` creates a policy.
- `PATCH /api/v1/admin/rate-limits/<policy_id>` updates a policy.
- `DELETE /api/v1/admin/rate-limits/<policy_id>` deletes a policy.

Admin policies can target one key, user, team, or MCP server, and admins can pause them without deleting them. Config policies appear on the same page as read-only entries. Admins can't enable a policy that would take its operation past 100 enabled policies.

An admin change applies straight away on the replica that handled it, and on every other replica within `policy_refresh_seconds`. Changing a policy's operation, model or MCP server filter, period, or metric starts its counters from zero. Changing the limit or the name keeps them.

Policy changes are recorded in the [admin audit log](https://docs.oceans-llm.com/access/admin-audit-log).

## Observability

- The metric `gateway.rate_limit.decisions` counts checks by `rate_limit.operation` and `rate_limit.outcome` (`admitted`, `rejected`, or `store_error`). Requests that no policy matches are not counted.
- A rejected MCP call appears in [MCP invocations](https://docs.oceans-llm.com/mcp/mcp-invocations) with status `policy_denied`, policy result `denied`, and error code `rate_limited`. Its metadata names the policy, scope kind, metric, period, limit, and retry delay.
- A rejected inference request writes no request-log row, so a client hammering the limit can't flood the request log. The gateway logs a `request rejected by rate limit` event with the operation, policy name, and client IP.

## Client IP and trusted proxies

The gateway records the client IP for each inference and MCP request. By default it's the TCP peer. Behind a load balancer or ingress, an admin lists the proxies in `server.trusted_proxies` so the gateway reads `X-Forwarded-For`:

```yaml title="gateway.yaml"
server:
  trusted_proxies:
    - 10.0.0.0/8
    - fd00::/8
```

The gateway reads `X-Forwarded-For` only when the peer is a trusted proxy. It walks the header from the right, skips trusted hops, and takes the first untrusted address, so a caller can't choose its own IP by sending the header. [Admin audit entries](https://docs.oceans-llm.com/access/admin-audit-log#request-ip) use the same resolution. Rate limits don't key on IP. For the rest of the `server` section, see the [configuration reference](/configuration/).

## Limits

- Batches, `/v1/models`, and admin APIs are not rate limited.
- A specific policy can't raise a default for one principal.
- Rate limits can't key on client IP.
