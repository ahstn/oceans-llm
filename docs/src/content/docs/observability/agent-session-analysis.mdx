Oceans groups related gateway requests into agent sessions and analyses each session after it ends. A report shows the request outcome, normalised cost, active time, score confidence, data coverage, the comparison group and the formula versions. It doesn't read prompts or judge the quality of an agent's answer.

The design and its limits are in the [passive agent session analysis ADR](https://github.com/ahstn/oceans-llm/blob/main/docs/adr/2026-07-21-passive-agent-session-analysis.md).

## Turn on analysis and access

Collection and access are separate. The gateway collects session data by default (`agent_analysis.enabled` is `true`), but nobody can see it until an admin turns on one of the access modes. All fields, defaults, validation rules and environment variable overrides are in the [`agent_analysis` configuration reference](/configuration/#agent_analysis).

| Mode | Fields | Who sees sessions |
| --- | --- | --- |
| Collect only (default) | `enabled: true` | Nobody. The page is hidden. |
| Calibration data | `shadow_diagnostics_enabled: true` | Platform admins. Scores show as **Score not shown**. |
| Calibrated scores | `calibrated_score_enabled: true` and a non-empty `calibration_approval_id` | Platform admins, with scores. |
| Team admin access | The calibrated score fields and `team_admin_enabled: true` | Platform admins, and team owners and admins for their own team. |

A safe first rollout collects facts and keeps the page hidden. Turn on `shadow_diagnostics_enabled` after platform admins agree on access and retention. The gateway checks only that `calibration_approval_id` is set: it doesn't check that any review took place. So set it only after your organisation has reviewed session grouping, score sensitivity, comparison groups and pricing.

Restart the gateway after any change. Each metric switch under `agent_analysis.metrics` controls one group of diagnostics. Metric, context and cache-profile changes create a new report version, so an admin then [recomputes retained sessions](#recompute-retained-sessions).

<Aside type="tip" title="Local dev stack">
`mise run dev-stack` seeds demo sessions and turns on calibration data by default, so the seeded platform admin can open the page at once. Set `AGENT_ANALYSIS_SHADOW_DIAGNOSTICS_ENABLED=false` before you start the stack to see the hidden state.
</Aside>

## Who can see sessions

The gateway enforces access on every list and detail request:

- Platform admins can see all sessions in the calibration data and calibrated score modes.
- Team owners and team admins can see sessions for their own team only, and only when calibrated scores and team admin access are both on. A team filter never grants access to another team's session detail.
- Team members and inactive users can't see sessions.

The signed-in session response tells the admin UI which access the gateway allows. When access is off, the gateway removes **Agent Sessions** from the navigation, and a direct visit goes to the user's default page. Team admins also need the `agent_sessions` page in [`permissions`](/access/access-settings/#pages-and-actions) to see the navigation item.

## Browse sessions

An admin opens **Observability** → **Agent Sessions** (`/admin/observability/agent-sessions`). The list is paged on the server. It shows 50 sessions per page by default, and the admin can choose 25, 50 or 100.

Open **Filters** to narrow the list by:

- **Session state** (open or finalised), **Outcome**, **Score maturity** and **Score confidence**.
- **Harness**, **Model**, **Operation** and **Caller class**.
- **User ID**, **Team ID** or **Service account ID**.
- **Session source ID** or **Session source hash**, the session identifier the harness sent.
- **Request tag key** and **Request tag value**. A value needs a key.
- **Minimum coverage**, **Started after** and **Started before**.

The URL stores the filters and the selected `session_id`, so a refresh, the browser history or a shared link opens the same view.

The table shows **Started**, **Harness**, **Model**, **State**, **Score** with its confidence, **Cost**, **Active time**, **Requests**, **Tool calls**, **MCP calls** and **Data quality**. **Data quality** says **Complete** or gives the number of data limits.

![Agent Sessions page with the Session explorer table of finalised opencode and Codex sessions, each showing Score not shown, cost, active time, request and tool counts, and its data limits](/images/agent-sessions-page.png)

Select a row to open the detail sheet. It shows the session score, normalised cost and total time, then any data limits. Below that are these sections:

- **Event stream**: each request in order, with route attempts, model changes, finish reasons, tool and skill activity and file activity. Each request links to its request log if you can see request logs.
- **Tool exposure**: supplied tools split into **Used at least once** and **Never called**.
- **Session identity**: the model, harness, gateway session ID and whether the harness sent a session source.
- **Score components**, **Token and cache use**, **Tools and changes** and **Prompt context**.

A section turned off in `agent_analysis.metrics` says "Disabled by the analysis configuration." A section with no measured data says "Unknown". Missing data stays missing: it isn't shown as zero.

## How sessions are formed

Oceans adds a request to a session after it writes the request log, in a background task. Analysis never delays the model response. If the gateway doesn't write a request log for a request, that request isn't analysed. Under heavy load, the gateway can skip analysis for a request rather than wait.

Oceans first uses session data that supported harnesses send, such as known session headers and permitted request metadata. It keeps this data inside the owner and harness scope that sent it. A [payload policy](/observability/request-logs/#payload-policy) can stop Oceans from reading body metadata. If a request has no usable session data, Oceans groups it into a window for that owner and harness. Oceans doesn't create an external session identifier, and the grouping key never contains prompt or response content.

A new request joins an open session only when the owner, harness, request tags and observed session source all match. A change of model, operation or caller doesn't start a new session.

A session ends after 30 minutes with no requests, or when it reaches 1,000 requests. The gateway then queues it for analysis. New data for a session marks its old report as out of date and queues a new one.

## Read session data

- **Outcome** comes from the final HTTP result of each request. A session is succeeded, partial, failed or unknown. An unknown outcome stays unknown.
- **Normalised cost** separates fresh input, cache reads, cache writes and output when the provider reports them and prices exist. See [Pricing catalog and accounting](/spend/pricing-and-accounting/).
- **Active time** joins overlapping request periods and short permitted gaps. It's shorter than elapsed time when the agent waits between requests.
- **Score confidence** describes the quality of the data, not the quality of the answer.
- **Data coverage** shows which request and response data was available and whether response data was incomplete.
- **Detected activity** lists request-level classifications. Each record keeps the parser version that made it.
- **Comparison group** is a set of earlier successful sessions from the same owner that use compatible analysis versions. Oceans starts with the most specific group, then tries broader harness, model, operation and caller groups. A group needs at least six sessions. With no group, there's no score.
- **Analysis versions** identify the report, analyser, score policy, pricing policy, observation parser, session-boundary policy, input time, detected-activity set and comparison snapshot.

### How the score works

The score is from 0 to 100. It's a weighted geometric mean of three parts:

| Part | Weight | Value |
| --- | --- | --- |
| Outcome | 0.5 | 1 for success, the success share for a partial outcome, 0.5 for unknown, 0 for failure. |
| Cost rank | 0.3 | How cheap the session is compared with its comparison group. |
| Active-time rank | 0.2 | How fast the session is compared with its comparison group. |

If cost or time is missing, the formula shares the weight among the parts that remain. If both are missing, there's no score. A failed outcome gives a score of `0`, so `0` and **Not available** mean different things. Each repeated request above the context boundary can then take off the configured penalty points.

## Read diagnostic groups

The detail sheet shows a subset of the report. The API response holds the full report.

### Tokens and cache

- **Total input** adds fresh input, cache reads and cache creation. Some providers report cached tokens outside their normal input field, and the full sum stops that split from looking cheaper.
- **Visible output** removes reasoning tokens only when the output count includes them. The report never subtracts reasoning twice.
- **Cache read to write ratio** compares cache reads with cache writes.
- **Cache write amplification** compares cache writes with cache reads. A high value can mean many writes with little reuse.
- **Cache threshold misses** count requests that asked for caching but stayed below the provider's minimum prefix and showed no cache activity. Cache profiles set the minimum cacheable prefix and the default cache lifetime for each provider and model. They don't invent token counts.
- **Cache read cost** and **Cache write cost** use the active price for each request.

Provider rules differ, and they change. Check the current [Anthropic prompt-caching guide](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [OpenAI prompt-caching guide](https://platform.openai.com/docs/guides/prompt-caching), [Amazon Bedrock prompt-caching guide](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html), [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) and [OpenAI pricing](https://platform.openai.com/docs/pricing) before you change a cache profile.

### Prompt context

The default boundary is 220,000 input tokens, with 128,000 tokens reserved for output. It's an operating limit, not the model's advertised context window. Keep it lower than the model's limit, because long prompts cost more and can reduce answer quality. The report shows the initial, median and maximum prompt size against the boundary, growth per turn, and possible context compactions. A warning isn't a claim about answer quality. For the research behind the boundary, see [Chroma's Context Rot evaluation](https://github.com/chroma-core/context-rot), the [NoLiMa long-context study](https://aclanthology.org/2025.findings-emnlp.1264/) and [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/).

### Reliability and tools

- **Wasted attempts** are route attempts that didn't produce the final response. The report includes their latency. Their cost stays unknown because providers don't report usage for each attempt.
- **Tool reliability** groups failures, truncation, latency and the input tokens used after a failure. It includes direct MCP calls and classified calls from other tool systems.
- **Tool servers** combine catalogue size, actual use, failures, schema size and uncached schema cost. Large catalogues can raise spend and reduce tool-selection accuracy: [RAG-MCP](https://arxiv.org/abs/2505.03275) and Anthropic's [context engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) explain why.

### Skills and file activity

Skill data separates the description tokens that are always loaded from the skill bodies and resources that load when selected. It can show a skill that was selected and then not used. The report stores only bounded names, token estimates and state flags, never skill files. See the [Agent Skills specification](https://agentskills.io/specification) for the skill format.

File activity uses opaque file IDs. It shows reads, searches, edits, creates and overwrites, possible rework, checks after writes, and failed file operations. These are operating signals. They don't prove that a change was correct.

### Finish reasons

Finish reasons separate normal completion from length or output-limit stops. A request stopped by a length limit can use input and reasoning tokens but return little visible output. This is a diagnostic, not a judgement of the model.

## Recompute retained sessions

After a change to metrics, context or cache profiles, an admin queues retained sessions for a new report. The command queues up to 100 finalised sessions whose latest report is missing or out of date:

```sh
# Local, against gateway.yaml
mise run //gateway:recompute-agent-analysis
# Against gateway.prod.yaml
mise run //gateway:prod:recompute-agent-analysis
# Any deployment
gateway recompute-agent-analysis --limit 500
```

Set `LIMIT` (mise) or `--limit` to a value from `1` to `1000`. To queue one session, run `gateway recompute-agent-analysis --session-id <UUID>` without `--limit`. The two flags can't be used together.

The command prints `matched_count` and `enqueued_count`. Running it again for the same session data and versions queues nothing new. It only queues work: the gateway's analysis worker builds the reports, and it runs only when `agent_analysis.enabled` is `true`.

## Privacy and retention

By default, analysis doesn't store prompts, responses, tool arguments, tool results, source code, file contents, file paths, hosts, IP addresses or arbitrary request headers. Diagnostics keep bounded tool and skill names, token estimates, attempt status, provider and model keys, finish reasons, operation classes and opaque file IDs. The gateway hashes each file ID with the owning user, team or service account before it stores it, so the same file can't be matched across owners. The request [payload policy](/observability/request-logs/#payload-policy) decides how much permitted metadata exists to detect optional activity.

Retention works like this:

- Reports expire after `report_retention_days` (default 90).
- Completed or failed queue records expire after `queue_retention_days` (default 7).
- An hourly job deletes expired reports and queue records, even when `agent_analysis.enabled` is `false`.
- Deleting a user or service account deletes their reports.

<Aside type="caution" title="Request-log purge also removes reports">
When [request-log purge](/observability/request-logs/#retention-and-purge) runs, it also deletes the analysis data for finalised sessions older than the purge cutoff. That removes their requests, detected activity and reports, then the sessions themselves unless they're queued for analysis. So when purge is on, reports last only as long as the request-log retention window, not the full `report_retention_days`.
</Aside>

## Limits

- The gateway doesn't check that calibration reviews happened. It shows calibrated scores as soon as `calibrated_score_enabled` and `calibration_approval_id` are set.
- The detail view shows at most 1,000 requests and 1,000 detected activities. Tool, skill and file facts share a limit of 2,048 per session. The sheet tells you when it doesn't show everything.
- Comparison groups look back 90 days.
- Provider cache fields can be missing or mean different things. The UI shows the coverage and data limit instead of an estimate.
- Session grouping is an operating estimate. It doesn't identify a person or prove that requests belong to the same conversation.
- The harness label used for grouping comes from the self-reported `User-Agent`. See [Agent harness usage](/observability/agent-harness-usage/).
