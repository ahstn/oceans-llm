The audit log records changes to the control plane: who changed what, when, from where, and what the change was. It covers keys, identities, budgets, rate limits, sessions and MCP access. It's separate from [request logs](/observability/request-logs/), which record model and tool traffic.

## Where to find it

- In the admin UI, a platform admin opens **Audit Log** under **Observability**, at `/admin/observability/audit-log`.
- Through the API, `GET /api/v1/admin/audit-logs` lists entries. It needs an active platform-admin session. An API key isn't accepted.

The **Control-plane changes** table has these columns:

| Column | Shows |
| --- | --- |
| **Time** | When the change happened, in UTC. |
| **Change** | The target type and the action, for example `MCP server` and `Updated`. |
| **Target** | The target's name and ID at the time of the change. |
| **Actor** | Who made the change: a user, an API key or the system. |
| **IP address** | The address of the request. See [Request IP](#request-ip). |

An admin selects a row to open the entry. The entry also shows the **User agent**, **Before** and **After** (redacted summaries of the target's state) and **Details** (extra context, including the request ID). A value the gateway didn't record shows as "Not recorded".

The **Actor** column names the person, not how they acted. A user can act through a session, an invitation link or an identity provider callback, and all of these show as a user. Sign-in entries (`session.created`) and invite redemptions (`user.invite_redeemed`) record the sign-in method in **Details**.

## What is audited

| Area | Actions |
| --- | --- |
| API keys | `api_key.created`, `api_key.updated`, `api_key.scopes_updated`, `api_key.revoked`, `api_key.secret_revealed` |
| Users | `user.created`, `user.updated`, `user.deactivated`, `user.reactivated`, `user.onboarding_reset`, `user.invite_issued`, `user.invite_redeemed`, `user.password_changed`, `user.provisioned`, `user.team_transferred` |
| Teams | `team.created`, `team.updated`, `team.members_added`, `team.member_removed` |
| Service accounts | `service_account.created`, `service_account.updated`, `service_account.disabled` |
| Budgets | `budget.set`, `budget.deactivated`, `budget.increase_created` |
| Sessions | `session.created` (password, OIDC or OAuth sign-in), `session.revoked` (sign-out) |
| MCP servers | `mcp_server.created`, `mcp_server.updated`, `mcp_server.disabled`, `mcp_server.enabled`, `mcp_server.discovery_refreshed`, `mcp_server.ownership_transferred` |
| MCP tool sets | `mcp_toolset.created`, `mcp_toolset.updated`, `mcp_toolset.disabled`, `mcp_toolset.tools_replaced` |
| MCP grants | `mcp_grant.set`, `mcp_grant.revoked` |
| MCP tools | `mcp_tool.tags_updated`, `mcp_tool.annotations_overridden`, `mcp_tool.version_approved`, `mcp_tool.version_rejected` |
| MCP tag rules | `mcp_tag_rule.set`, `mcp_tag_rule.revoked` |
| MCP credentials | `mcp_credential_binding.set` (create, replace, or a user's OAuth connect), `mcp_credential_binding.revoked` |
| MCP client grants | `mcp_client_grant.authorized`, `mcp_client_grant.denied` (a user's choice on the OAuth consent page), `mcp_client_grant.revoked` (by the user or a platform admin) |
| Provider credentials | `provider_credential.set`, `provider_credential.deleted` |
| Rate limits | `rate_limit_policy.created`, `rate_limit_policy.updated`, `rate_limit_policy.deleted` |
| Other | `pricing_catalog.refreshed`, `review_agent_repository.created`, `review_agent_repository.updated`, `review_agent_repository.disabled`, `review_agent_repository.reactivated` |

MCP client grants come from MCP clients that sign in with OAuth. See [MCP client setup](/extensions/mcp-client-setup/).

### When an entry is written

- A change that fails writes no entry. That includes validation errors, conflicts and denied permissions.
- A change that has no effect writes no entry either. Examples are revoking a revoked key, disabling a disabled MCP server, signing out twice with the same session, and saving a record unchanged.
- Some changes are made of several writes. If one write fails after another has landed, part of the change took effect. The gateway records it with `outcome: partial` and the error code in **Details**.
- `pricing_catalog.refreshed` is written on every refresh. **Details** lists each source's outcome, including sources that were unchanged or failed.
- An invited user's first OIDC or OAuth sign-in records `user.invite_redeemed`, as setting a password from an invite does.
- The gateway writes the entry after the change is committed. If that write fails, the gateway logs an error and the change still stands.

MCP admin changes also record the actor's scope in **Details**. `actor_access` is `platform_admin` or `team_admin`. `actor_team_id` and `actor_team_role` name the actor's team and role when they belong to one. A user's own OAuth connections and consent decisions don't carry these fields. Publishing or unpublishing a server shows as a `visibility` change in `mcp_server.updated`. The reasoning is in the [delegated MCP server ownership ADR](https://github.com/ahstn/oceans-llm/blob/main/docs/adr/2026-10-17-delegated-mcp-server-ownership.md).

### Not recorded

- Failed sign-in attempts and session refreshes.
- Model traffic, MCP tool calls, batches and Skills publishing. [Request logs](/observability/request-logs/) and [MCP invocations](/extensions/mcp-invocations/) cover traffic.
- Guardrail policy, because it's set in `gateway.yaml` and has no admin edit endpoint.
- Deleting an MCP server, because the API only disables and enables servers.

## Redaction

Audit entries are built without secret values, and a safety net checks them again before they're stored:

- **Secrets and credentials.** Raw API keys, passwords, session cookies, invite links and tokens, MCP upstream secrets, OAuth tokens and provider tokens are left out of the summaries. An `api_key.secret_revealed` entry doesn't contain the secret.
- **Credential bindings.** Bindings record metadata only, such as the kind, header name, secret reference, scopes and expiry.
- **Server URLs.** MCP server URLs are stored without credentials, query strings or fragments. Path segments that look like tokens, including percent-encoded ones, are replaced.
- **Safety net.** Values under secret-looking field names, and strings that look like credentials (including URLs with a username or password), become `[REDACTED]`. Known provider token formats, the same ones the prompt guardrails detect, become `[REDACTED:<rule>]`.

Target names longer than 256 characters are truncated. A summary larger than 16 KiB is replaced with a marker that gives its size.

## Filtering and paging

The list is newest first. These query parameters filter it:

| Parameter | Filters by | UI filter |
| --- | --- | --- |
| `target_type` | Target type, such as `api_key` | **Target type** |
| `action` | One exact action, such as `api_key.created` | **Action** |
| `target_id` | Target ID | **Target ID** |
| `actor_user_id` | The user who made the change | **Actor user ID** |
| `occurred_at_start`, `occurred_at_end` | Time range, inclusive, in RFC 3339 | none |

In the UI, an admin can also select a user's name in the **Actor** column to filter by that user. The UI has no date fields, but it accepts the time parameters in the page URL.

The list leaves out each entry's before, after and details summaries. `GET /api/v1/admin/audit-logs/{audit_log_id}` returns one entry with them.

Pages use a cursor, not page numbers. Pass the response's `next_cursor` as `cursor` to fetch older entries. `next_cursor` is `null` on the last page. `limit` defaults to 50, and the gateway lowers any value above 200 to 200. In the UI, **Newest** and **Older** move between pages.

```bash
curl -s -b "ogw_session=$SESSION" \
  "$GATEWAY/api/v1/admin/audit-logs?target_type=api_key&limit=100"
```

## Request IP

The gateway records the address that connected to it. If that address is listed in [`server.trusted_proxies`](/spend/rate-limits/#client-ip-and-trusted-proxies), it reads `X-Forwarded-For` instead, as it does for rate limits. Behind a load balancer, entries then record the browser, not the load balancer. The list is empty by default.

For changes made in the admin UI, the admin UI proxy resolves the address in the same way and signs it. The gateway uses the signed address when the signature is valid and recent. The proxy drops any signed-address header the client sends, so a client can't forge its address with `X-Forwarded-For` or its own signed header.

## Retention

The gateway never deletes audit entries, and there's no setting to purge them. Request-log purge doesn't remove audit entries.
