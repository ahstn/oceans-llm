A service account is a gateway identity for software: CI jobs, applications, bots and other non-human callers. Each one belongs to one team, has its own budget, and calls the gateway with its own API keys. Use a service account whenever traffic shouldn't spend against one person. For how service accounts fit with users and teams, see [Identity and access](/access/identity-and-access/).

## How service accounts work

- Every service account belongs to exactly one team. The team can't change later.
- A service account is not a user. It can't sign in to `/admin`.
- Its API keys can call `/v1/*` and the MCP routes, within their model grants, scopes and MCP grants.
- Spend from its keys counts against the service account. Reports show it under the service account and its team.
- Its lifecycle is separate from team membership. Adding, removing or moving team members doesn't change it.
- Its keys work only while the service account has an active budget.

An API key is a credential, not the identity. A team's automation calls the gateway with a key that belongs to a service account. Keys can't belong to a team directly.

## Create a service account

<Steps>
<Step title="Create the account">
A platform admin, or an owner or admin of the team, creates the service account in one of two ways:

- In config, with an entry in `service_accounts`. The gateway creates or updates it at startup. See [Auth and access settings](/access/access-settings/#service_accounts).
- With the admin API: `POST /api/v1/admin/identity/service-accounts` with `team_id`, `name`, and optional `tags`. The gateway makes the account's key from its name. The team must be active.

The **Service Accounts** page in the admin UI is read-only. It can't create or change service accounts.
</Step>
<Step title="Give it a budget">
A service account needs an active budget before it can have working keys. Set `budget` on the config entry (it's required there), or have a platform admin select **Configure** on the account's row in the **Service accounts** tab of **Spend Controls**. Team owners and admins can't set budgets. See [Budgets](/spend/budgets/).
</Step>
<Step title="Create a key">
An admin opens **API Keys**, selects **Create API key**, and sets **Owner type** to **Service account**. Service-account keys always use explicit model grants, so the admin picks the **Granted models**. Config can also declare keys under `service_accounts[].keys`.

The gateway stores service-account key secrets encrypted, so allowed admins can reveal them later. This needs `OCEANS_API_KEY_SECRET_ENCRYPTION_KEY`. See [Auth and access settings](/access/access-settings/#service_accounts).
</Step>
</Steps>

## Who can manage service accounts

What an admin can do depends on their scope:

| Action | Platform admin | Team owner or admin | Team member |
| --- | --- | --- | --- |
| See active service accounts | All teams | Own team | Own team, without key details |
| Create, rename, retag or deactivate | All teams | Own team | No |
| Create, update and revoke keys | All teams | Own team | No |
| Reveal stored key secrets | All teams | Own team | No |
| Set or remove the budget | Yes | No | No |

Key actions also depend on the `create_api_key`, `update_api_key`, `revoke_api_key` and `reveal_api_key` permissions in config. See [Auth and access settings](/access/access-settings/#permissions). People outside the team can't see or manage its service accounts, unless they are platform admins.

The **Service Accounts** page lists each account with its key, team, status, tags and API keys. **Open API key** goes to the key on the **API Keys** page. A regular member sees "Credential details restricted" in place of the key name. A user with no team sees no service accounts.

## Deactivate a service account

Deleting a service account deactivates it. An admin sends `DELETE /api/v1/admin/identity/service-accounts/<service_account_id>`. After that:

- The account stays in all past records.
- Its keys stop working at once, without being revoked one by one. A request with one of these keys currently fails with `500 api_key_owner_invalid`.
- Past request logs and spend records keep the service account as their owner.

There is no way to reactivate a service account. Reseeding from config doesn't reactivate it either. To restore access, create a new service account.

Revoking a key is different. It blocks only that one key. Deactivating the service account blocks every key it owns.

## Budget gate

A service-account key can't authenticate unless its service account has an active budget. Without one, the gateway returns `403 service_account_budget_required`. The gateway also refuses to create a key for a service account with no active budget.

The gateway won't deactivate a service-account budget while the account has active keys. Revoke the keys first, or deactivate the service account.

Service-account traffic is checked against the service account's budget only, not the team's. See [Budgets](/spend/budgets/).

## Budget alerts

Service-account budget alerts go to the people who can act for the team: its active owners and admins. The gateway picks the recipients when it creates the alert. Disabled users, removed members, ordinary members and people outside the team don't get them. If no one qualifies, the alert delivery is recorded as failed.

## Model access

Service-account keys follow the same model access layers as other keys, with these differences:

- A service-account key must use explicit model grants. `model_grant_mode: all` is rejected.
- User model restrictions don't apply, because a service account is not a user.
- The gateway always refuses a service-account key for a model that has an `allowlist`, even when the team is listed. Use a user-owned key for those models, or remove the `allowlist`.

See [Identity and access](/access/identity-and-access/#model-access) for the full layers.

## Provider credentials are separate

A gateway service account is not a cloud-provider service account. For example, a Vertex provider can use a Google Cloud service-account file:

```yaml title="gateway.yaml"
providers:
  - id: vertex
    type: gcp_vertex
    auth:
      mode: service_account
      credentials_path: /var/run/secrets/gcp/service-account.json
```

This `service_account` mode is how the gateway signs in to Google Cloud to call Vertex. It doesn't create a gateway service account, give any caller access to `/v1/*`, or take part in team rules. See [Google Vertex AI](/providers/gcp-vertex/).

## Limits

- The admin UI can't create, edit or deactivate service accounts. Use config or the admin API.
- A deactivated service account can't be reactivated.
- A service account can't move to another team.
- Service-account tags can't be edited in the admin UI.

The design is in the [team service accounts ADR](https://github.com/ahstn/oceans-llm/blob/main/docs/adr/2026-05-10-team-service-accounts.md).
