Users can sign in to the admin UI with any OpenID Connect (OIDC) provider, such as Authentik, Okta or Google, or with GitHub OAuth. Every method ends the same way as password sign-in: the gateway sets the `ogw_session` cookie and the user opens `/admin`. The pages a user sees depend on their role and the `permissions` config, not on how they signed in. See [Identity and access](/access/identity-and-access/) for roles and the user lifecycle.

This page explains how SSO sign-in works and how Oceans decides who may sign in. The YAML fields are on [Auth and access settings](/access/access-settings/). For provider setup, see [Google OAuth and OIDC setup](/access/sso/google/) and [GitHub OAuth setup](/access/sso/github/).

## Supported providers

| Provider | Config list | Callback path |
| --- | --- | --- |
| Any OIDC provider, including Google | `auth.oidc.providers` | `/api/v1/auth/oidc/callback` |
| GitHub | `auth.oauth.providers` with `provider_type: github` | `/api/v1/auth/oauth/callback/github` |

GitHub is the only OAuth provider type. The gateway builds each callback URL from the section's `public_base_url`. Set it to the public origin that browsers use, for example `https://oceans.example.com`. It's required when a GitHub provider is enabled. For OIDC, if you don't set it, the gateway uses the request origin: the `X-Forwarded-Origin` header, or `X-Forwarded-Proto` and `Host`. That guess can be wrong behind a proxy, so set it.

Providers reach the login page through the config seed, the same as users and models. A provider change takes effect only after the seed runs. The gateway resolves the client secret again at each sign-in, so the secret's environment variable or file must stay available to the gateway process. See [Start up and first access](/setup/first-access/) for when seeding runs.

## How sign-in works

<Steps>
  <Step title="The user opens the login page">
    `/admin/login` shows one button for each enabled provider, below the password form. Each button shows the provider's `label`.
  </Step>
  <Step title="The gateway sends the user to the provider">
    The gateway creates a one-time `state` value and a PKCE challenge (and a nonce for OIDC). It stores them for 10 minutes, then redirects to the provider. For OIDC, it first fetches the provider's discovery document from `issuer_url`.
  </Step>
  <Step title="The provider returns to the callback">
    The gateway uses up the `state` value and exchanges the code for tokens. For OIDC, it verifies the ID token and the nonce, and needs an `email` claim with `email_verified: true`. For GitHub, it reads the numeric user id from `/user` and the primary email from `/user/emails`, then applies the email verification and allowed-domain rules.
  </Step>
  <Step title="Oceans matches the identity to a user">
    See [How Oceans matches an identity](#how-oceans-matches-an-identity).
  </Step>
  <Step title="The gateway creates the session">
    The gateway sets `ogw_session` (HttpOnly, `SameSite=Lax`, valid for 30 days) and redirects to `redirect_to`. The cookie is marked `Secure` when the proxy reports HTTPS through `X-Forwarded-Proto` or `X-Forwarded-Origin`. The admin UI then opens the user's profile page, `/admin/profile`, or `/admin/no-access` if the user has no pages.
  </Step>
</Steps>

The gateway fetches the OIDC discovery document on every start and every callback, so it must be able to reach `issuer_url` over the network.

## Start SSO sign-in

The shared login page is the normal entry point for every SSO user:

```text
https://<your-oceans-host>/admin/login
```

The user picks the provider that an admin set up for them and signs in. On the first successful match, Oceans records the provider's subject id, changes the user from `invited` to `active`, and creates the session. An SSO user doesn't need a personal invite link.

Before you share the login page, seed the provider and user config for your deployment. See [SSO users seeded by config](/setup/first-access/#sso-users-seeded-by-config).

### Direct start URLs

Use a start URL when a link must skip the provider choice:

```text
https://<your-oceans-host>/api/v1/auth/oidc/start?provider_key=<oidc-provider-key>&redirect_to=%2Fadmin
https://<your-oceans-host>/api/v1/auth/oauth/start?provider_key=<oauth-provider-key>&redirect_to=%2Fadmin
```

The start URL is stable. Each request creates fresh `state` and PKCE values. Don't copy and share the provider URL that the browser is redirected to, because its `state` works once and expires after 10 minutes.

| Parameter | Required | Behaviour |
| --- | --- | --- |
| `provider_key` | Yes | The `key` of an enabled provider. An unknown or disabled key fails. |
| `login_hint` | No | Must be an email address, or the request fails. OIDC providers get it as `login_hint`. GitHub gets it as `login`. It can preselect an account, but the provider may ignore it. Oceans never treats it as proof of identity. |
| `redirect_to` | No | Where the browser goes after sign-in. It must start with `/admin`, not start with `//`, and contain no backslash. A missing or invalid value becomes `/admin/account-ready?mode=oidc` (or `mode=oauth`). The login page sends `/admin`, or the admin page the user tried to open. |

### Per-user sign-in URLs

When a platform admin adds an SSO user on the **Users** page (under **Identity**) with **Add user**, and picks **SSO (OIDC)** or **SSO (OAuth)** as the **Auth method**, the dialog shows **SSO sign-in URL ready** with a URL to copy. That URL is a direct start URL with the user's email as `login_hint`. After sign-in it opens the **Account ready** page, which moves on to the control plane after a short pause.

The URL contains no secret and gives no more access than the shared login page. Password invites are different: they contain a single-use token, expire after 7 days, and are the only way for a password user to finish onboarding.

## How Oceans matches an identity

After the provider returns, Oceans checks these rules in order. Emails are compared after trimming and lowercasing.

1. **Existing link.** If a user is already linked to this provider and subject id, that user signs in. A disabled user is refused. An invited user is activated.
2. **Invited user for this provider.** If an `invited` user has the same email, is set up for this provider key, and has no link yet, Oceans links the subject id and activates the user.
3. **Email already in use.** If any other user has the same email, Oceans refuses the sign-in with `identity_conflict`. This covers password users and users set up for a different provider. Oceans never links an existing account by email alone.
4. **JIT.** If the provider has `jit.enabled: true`, Oceans creates an active user. The name is the part of the email before `@`. The global role, team membership and request logging setting come from the provider's `jit` block.
5. **No match.** Oceans refuses the sign-in with `unmatched_identity`.

For GitHub, the email verification and allowed-domain rules run before step 1. A GitHub account that fails them can't sign in, activate an invite, or be created by JIT.

JIT applies the same fixed defaults to every new user. It doesn't read groups or claims from the provider. No user becomes `platform_admin` unless `jit.global_role` says so, and that role then applies to everyone the provider lets through. See [JIT fields](/access/access-settings/#jit-fields).

Password sign-in stays available for password users until an admin disables them. An existing password user can't switch to SSO by signing in with a matching email. To move a user to SSO, a platform admin opens the user on the **Users** page and goes to the **Auth & onboarding** tab. The admin selects **Deactivate** if the user is active, then **Reset onboarding**, which puts the user back to `invited`. The **Auth method** can then be changed.

## Sign-in errors

When SSO sign-in fails after the provider redirect, the gateway sends the browser to `/admin/login?sso_error=<code>`. The login page shows **SSO sign in failed** with the message below.

| Code | Message shown | Cause |
| --- | --- | --- |
| `access_denied` | Access was denied for this SSO account. | The provider returned an error, for example the user cancelled. |
| `denied` | Access was denied for this SSO account. | The matched Oceans user is disabled. |
| `unmatched_identity` | This SSO account is not allowed to sign in. | No user matched and JIT is off. Also: no `email` claim or `email_verified` isn't `true` (OIDC), the email domain isn't allowed, or GitHub returned no primary email or the email lookup failed. |
| `github_unverified_email` | GitHub did not return a primary verified email for this account. | The GitHub primary email isn't verified and `sso_email_verification_enabled` is `true`. |
| `identity_conflict` | A password account already exists for this email address. | Another Oceans user has this email. That user may be a password user or an SSO user for a different provider. |
| `state_invalid` | The SSO sign-in request could not be verified. | The `state` value is missing, unknown or already used. |
| `state_expired` | The SSO sign-in request expired. | More than 10 minutes passed between start and callback. |
| `provider_failure` | The identity provider did not complete sign-in. | The code exchange failed, no ID token came back, the ID token failed verification, or the GitHub user lookup failed. |

Some failures return an error response instead of the login page: an unknown or disabled `provider_key`, an invalid `login_hint`, or a failed OIDC discovery request. The gateway logs the detail for token exchange, ID token and GitHub lookup failures.

## Limits

- Oceans doesn't map provider groups or claims to roles or teams.
- OIDC providers have no `allowed_email_domains` setting. The gateway ignores unknown keys in provider entries, so adding it to an OIDC provider has no effect. Restrict sign-in at the identity provider instead, for example with an Internal Google audience.
- Oceans doesn't check Google's `hd` (hosted domain) claim.
- The gateway doesn't cache OIDC discovery or signing keys between sign-ins.

## MCP client sign-in

When `mcp.client_oauth` is enabled, MCP clients sign users in through the same admin session. The gateway's `/oauth/authorize` endpoint sends the browser to `/admin/oauth/consent`. A signed-out user signs in at `/admin/login` with any method, SSO included, and comes back to the consent page. Tokens issued after consent are tied to that session: sign-out, session expiry or deactivation ends them. See [MCP client setup](/extensions/mcp-client-setup/).

## Try SSO locally

The repository ships an Authentik identity provider for local testing. The `sso` profile in `compose.local.yaml` starts Authentik with a blueprint that creates the `Oceans LLM` application and a test user. The local gateway also needs a bootstrap admin password of at least 16 characters:

```shell
export GATEWAY_BOOTSTRAP_ADMIN_PASSWORD="$(openssl rand -base64 24)"
BUN_VERSION="$(mise tool bun --requested)" RUST_VERSION="$(mise tool rust --requested)" docker compose --profile sso -f compose.local.yaml up --build
```

Open `http://localhost:8080/admin/login`, choose **Authentik**, and sign in as `sso-user@example.com` with the password `sso-user-password`. The local config, [`deploy/config/gateway.local.yaml`](https://github.com/ahstn/oceans-llm/blob/main/deploy/config/gateway.local.yaml), turns on JIT for Authentik, so the first sign-in creates a platform admin in the `platform` team. The `sso` profile in `deploy/compose.yaml` starts Authentik too, but [`deploy/config/gateway.yaml`](https://github.com/ahstn/oceans-llm/blob/main/deploy/config/gateway.yaml) leaves the Authentik provider disabled.

[Testing authentication locally](https://github.com/ahstn/oceans-llm/blob/main/docs/contributing/development/authentication-testing.md) has the full procedure, the Authentik admin account and the fixture details. The design is in the [Authentik local SSO test IdP ADR](https://github.com/ahstn/oceans-llm/blob/main/docs/adr/2026-05-15-authentik-local-sso-test-idp.md).
