The admin control plane is the browser UI at `/admin`. Admins use it to manage API keys, identities, spend, rate limits and MCP access. Users use it to see their own keys, spend and logs. Each person sees only the pages that their permission group allows.

## How it is served

The gateway serves the control plane at `/admin`, on the same origin as the API. It handles sign-in and the admin APIs, and it proxies page requests to the admin UI server. The admin UI then calls back into the gateway on the same origin. See [Topology and operations](/setup/deploy-and-operations/#one-origin-for-everything).

## Sign in and sessions

- A person signs in at `/admin/login` with a password or an SSO provider. See [OIDC and SSO](/access/sso/).
- If the account must change its password, the UI sends it to `/admin/change-password` before any other page. The bootstrap admin can be set up this way. See [Start up and first access](/setup/first-access/#the-bootstrap-admin).
- After sign-in, the UI opens the page named in the `redirect` parameter, if the person can open it. If not, it opens their profile at `/admin/profile`. A person with no pages who isn't a platform admin lands on `/admin/no-access` instead.
- The session is kept in the `ogw_session` cookie for up to 30 days. When the session is missing or has expired, the UI sends the person back to `/admin/login` and keeps the requested page in `redirect`.
- The account menu at the bottom of the sidebar has **Change password** and **Sign out**.

Scripts can use the same session. `GET /api/v1/auth/session` returns the current session, or `null`. `POST /api/v1/auth/logout` revokes the current session and clears the cookie.

## Who sees which page

The gateway puts each signed-in person in one permission group: `platform_admins`, `team_admins` (team owners and team admins) or `users`. The `permissions` config sets each group's pages and API-key actions, and the session carries the resolved sets. The sidebar shows only the pages in the set, and the UI blocks direct links to other pages.

Page grants only control the UI. They don't limit the admin APIs, which apply their own role and scope checks. [Auth and access settings](/access/access-settings/#permissions) has the syntax, the defaults and what each grant enforces. [Identity and access](/access/identity-and-access/) explains how the groups map to data scope.

Some pages don't follow page grants:

- **Profile**, **Agent Skills** and **Agent Plugins** are open to every signed-in person. So is **Workspace connections** at `/admin/account/connections`, which isn't in the sidebar.
- **Guardrail Settings**, **Guardrails** and **Audit Log** need the `platform_admin` role. The two guardrail pages also need the `mcp_invocations` page.
- **Rate Limits** needs the `platform_admin` role and the `rate_limits` page.
- **Batch Requests** follows the `request_logs` page grant.

## API keys

![API keys page listing keys with their owner, granted models, scopes, status and a Manage button](/images/screenshot-api-keys.png)

The **API Keys** page lists the keys in the person's scope, with each key's owner, granted models, scopes and status. By default, a user manages only their own keys. A team owner or admin also manages the service-account keys of their team, and a platform admin manages every key. The `create_api_key`, `update_api_key`, `revoke_api_key` and `reveal_api_key` actions can narrow this. See [Pages and actions](/access/access-settings/#pages-and-actions).

### Create a key

<Steps>
<Step title="Open the dialog">
The admin or user selects **Create API key**.
</Step>
<Step title="Choose the owner">
The owner is a user or a service account. There are no team-owned keys: team automation uses a key on a team-owned [service account](/access/service-accounts/). A service account needs an active budget before it can get a key.
</Step>
<Step title="Choose the models">
**All models** covers every model the owner may use, now and later. It's for user-owned keys only. **Selected models** grants an explicit list from the current model catalog, and is the only choice for service-account keys.
</Step>
<Step title="Choose the scopes">
**Full access** allows every key route. **Limited** allows only the scopes that are ticked: **Inference**, **MCP aggregate** and **MCP proxy**. A key that can use MCP can be limited to **Selected servers** instead of **All granted servers**. The owner still needs grants on each server.
</Step>
<Step title="Copy the key">
The new key appears once, under **Copy the new key now**. The person copies it with **Copy API key** before they dismiss the alert.
</Step>
</Steps>

The gateway never stores a user-owned key's raw secret, so a lost personal key can't be recovered: create a new one. For service-account keys, the gateway stores the secret encrypted with `OCEANS_API_KEY_SECRET_ENCRYPTION_KEY`. A team owner or admin for that team, or a platform admin, can show it again with **Reveal API key**, and the [audit log](/access/admin-audit-log/) records each reveal. A key without stored secret material can't be revealed.

### Change or revoke a key

The person selects **Manage** on an active key. In the **Manage API key** dialog they can replace the model access, the scopes and the MCP server list, then select **Save access**. Model access and scopes are saved as two requests, so if the second fails, the first change has still been applied.

**Revoke key** revokes the key. The gateway rejects every later request with that key with `401 api_key_revoked`. Requests that were already authenticated aren't stopped.

To rotate a service-account key, create a replacement key, update the caller's secret, then revoke the old key.

### API key limits

- A key can't be renamed or moved to another owner.
- A revoked key is read-only and can't be restored.
- Explicit model grants must name models in the current catalog.
- A service-account key fails at runtime with `403 service_account_budget_required` when its account has no active budget.

## Users and teams

Only platform admins change users and teams. The gateway checks this twice: a guard on every `POST`, `PUT`, `PATCH` and `DELETE` request under `/api/v1/admin/identity/users` and `/api/v1/admin/identity/teams`, and the same check again in each handler. Team owners and team admins can't change memberships or tags.

On the **Users** page, a platform admin can:

- Add a user with **Add user**, as a password user or an SSO user, and hand off the onboarding URL. Password invites expire after 7 days. A user can also be pre-provisioned against an enabled OIDC or OAuth provider.
- Open a user with **Manage** to change the global role, team and team role, and tags.
- **Deactivate**, **Reactivate** or **Reset onboarding** a user, on the **Auth & onboarding** tab.
- Store a user's GitHub Copilot token on the **Provider Configuration** tab. See [GitHub Copilot](/providers/github-copilot/).

On the **Teams** page, a platform admin can:

- Create a team with **Add team**, and change it, including its team admins, with **Edit team**.
- Add members with **Add members**: existing users who have no team, or new users with **Invite member**.
- **Transfer** a member to another team as `Member` or `Admin`, or **Remove** them.

A transfer changes membership only. It doesn't move past request logs, spend, budgets or API-key ownership.

### Identity limits

- Owner memberships can't be created, removed or transferred in these workflows.
- A user's auth mode can change only while the user is still invited.
- **Reset onboarding** works only for invited or disabled users.
- An admin can't deactivate their own account or remove their own platform admin role.
- The bootstrap admin is managed outside the normal user lifecycle.
- Oceans doesn't map OIDC groups or claims to roles. A provider's JIT settings can give new users a fixed role and team. See [OIDC and SSO](/access/sso/).

### Service accounts

The **Service Accounts** page is read-only for everyone. Service accounts come from the `service_accounts` config section or the admin API at `/api/v1/admin/identity/service-accounts`. Platform admins can manage service accounts in every team. Team owners and admins can manage those in their own team. Deleting a service account disables it. See [Service accounts](/access/service-accounts/).
