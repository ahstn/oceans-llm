A `models[*]` entry defines one gateway model that callers can request. Each model either has `routes` to providers or is an alias of another model. This page lists the fields and their validation rules. For how the gateway picks a route and gates a request, see [Model routing and APIs](/configuration/model-routing/). For provider fields, see [Providers](/configuration/providers/).

## Model fields

A model must set exactly one of `routes` or `alias_of`. Setting both, or neither, fails config loading. Unknown model fields are rejected.

| Field | Default | Notes |
| --- | --- | --- |
| `id` | required | The model name callers send. |
| `routes` | `[]` | Provider-backed routes. See [Route fields](#route-fields). |
| `alias_of` | none | Target model `id`. The target must exist. A model can't alias itself, and alias cycles fail. |
| `description` | none | Shown in the admin UI and model lists. |
| `tags` | `[]` | Used by `tag:` selectors. |
| `rank` | `100` | Display and ordering rank. |
| `routing` | none | Routing policy. Provider-backed models only. See [Routing policy and session affinity](#routing-policy-and-session-affinity). |
| `max_reasoning_effort` | none | See [Reasoning effort ceilings](#reasoning-effort-ceilings). |
| `service_tiers` | none | Non-default tiers callers may request. See [Service tiers](#service-tiers). |
| `allowlist` | none | See [Model allowlists](#model-allowlists). |
| `benchmark_model_id` | none | OpenRouter model ID (`publisher/model`, no `:variant`) for benchmark lookup. See [Configuration reference](/configuration/). |

A provider-backed model and an alias that points to it:

```yaml
models:
  - id: coding-default
    alias_of: coding-primary

  - id: coding-primary
    routes:
      - provider: openai-primary
        upstream_model: gpt-5
```

Callers can request either name. Access to one doesn't grant access to the other, so grant the name callers will send.

## Routing policy and session affinity

`models[*].routing` is optional and applies only to provider-backed models. An alias can't set `routing`: it inherits the resolved target's policy.

| Field | Default | Accepted values |
| --- | --- | --- |
| `routing.strategy` | `weighted_random` | `preferred`, `weighted_random`, `round_robin` |
| `routing.affinity` | absent (no session affinity) | An object. `{}` enables affinity with the default timeout. |
| `routing.affinity.idle_timeout_seconds` | `3600` | Integer from `1` to `4294967295` |

When `routing` is present, even as `routing: {}`, every route on the model needs an explicit `id`. Unknown routing fields and unknown strategy names fail config loading. Omitting `routing` keeps weighted selection without affinity.

This pool rotates new sessions between two provider connections:

```yaml
models:
  - id: coding-pool
    routing:
      strategy: round_robin
      affinity:
        idle_timeout_seconds: 3600
    routes:
      - id: primary
        provider: openai-primary
        upstream_model: gpt-6-sol
        priority: 10
        weight: 3
      - id: secondary
        provider: openrouter
        upstream_model: openai/gpt-6-sol
        priority: 10
        weight: 1
```

Under `round_robin` both routes get turns. The weights matter only if the strategy changes to `weighted_random`.

Routes on `aws_bedrock`, `gcp_vertex`, or `gcp_cloud_run_openai_compat` providers with ambient or file-based credentials also need the provider's [routing account scope](/configuration/providers/#routing-account-scope).

Routing policy is YAML-only. Apply changes by reseeding the deployment. For which APIs use the policy, session IDs, and response-origin tracking, see [Model routing and APIs](/configuration/model-routing/).

## Reasoning effort ceilings

`models[*].max_reasoning_effort` is an optional ceiling for explicit categorical reasoning effort.

```yaml
models:
  - id: claude-fable-5.1
    description: Claude Fable 5.1 on Vertex
    max_reasoning_effort: high
    routes:
      - provider: vertex-global
        upstream_model: anthropic/claude-fable-5-1
```

Accepted values, from least to most effort: `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. Omitting the field or setting `null` means no ceiling. The gateway compares values in this order. It doesn't clamp or rewrite requests.

Use `none` for a model that must not reason. With `none`, only requests that send `none` or `off`, or no effort, pass. Every other effort value is rejected. Support for `minimal` depends on the upstream model. For example, OpenRouter doesn't list `minimal` for GPT-6 Luna or Gemini 4 Hydrogen. Use `none` rather than `minimal` as the lowest ceiling for such models.

The ceiling covers categorical effort only. It doesn't cap numeric controls such as `thinking.budget_tokens` or `reasoning.budget_tokens`. It also doesn't govern a default the provider picks when neither the caller nor the route sets effort. If a provider default must respect the ceiling, set it explicitly on the route.

Startup checks explicit effort values in each route's `extra_body` against the ceiling. Known values above the ceiling, unknown strings, and non-string values fail config loading. Omitted and `null` values pass. For aliases, startup uses the strictest ceiling in the whole alias chain and checks the target's routes against it.

For request shapes and rejection behaviour, see [Model routing and APIs](/configuration/model-routing/).

## Service tiers

Providers sell some models at more than one capacity tier. The gateway knows four tiers:

| Tier | Aliases | Typical price | Notes |
| --- | --- | --- | --- |
| `default` | `standard` | 1× | The provider's normal tier. |
| `flex` | none | about 0.5× | Slower and can fail when the provider is busy. |
| `priority` | `fast` | about 2× | OpenAI Fast, Anthropic fast mode, Gemini and Bedrock priority. |
| `ultrafast` | none | about 6× | OpenAI Responses and OpenRouter, on a few models. |

Callers ask for a tier per request. See [Service tiers in requests](/configuration/model-routing/#service-tiers). Admins control tiers in two places.

**Limit the tiers of a model.** `service_tiers` lists the non-default tiers callers may request. When you omit it, callers may request every tier. `default` is always allowed, so don't list it.

```yaml
models:
  - id: deepseek-v4.1-flash
    service_tiers: [flex]
    routes:
      - provider: openrouter
        upstream_model: deepseek/deepseek-v4.1-flash
```

A request for a tier that isn't listed fails with 403 `service_tier_not_allowed`.

**Publish a fast model.** A route's `service_tier` fixes the tier of every request on that route. The route's tier wins over the caller's. Give the fast model its own `id`, so you can grant it, budget it and price it on its own.

```yaml
models:
  - id: gpt-6-luna
    routes:
      - provider: openrouter
        upstream_model: openai/gpt-6-luna

  - id: gpt-6-luna-fast
    routes:
      - provider: openrouter
        upstream_model: openai/gpt-6-luna
        service_tier: priority
```

Each provider type sends the tier in its own form. The tiers can depend on the API, the location and the model:

| Provider type | Tiers | Sent as |
| --- | --- | --- |
| `openai_compat` to OpenRouter | all, on Chat Completions, Responses and Messages | `service_tier` in the body |
| `openai_compat`, other hosts | Responses: all. Chat Completions and Messages: all except `ultrafast`, because OpenAI's Chat Completions API has no `ultrafast` value ([Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create.md)). | `service_tier` in the body |
| `anthropic_compat` | `default`. `priority` only on Claude Fable 5.2, Mythos 5.2, Opus 5.5, Opus 5 and Opus 4.8 (until 2026-11-30) ([fast mode](https://platform.claude.com/docs/en/build-with-claude/fast-mode.md)). | `speed: "fast"`, with the fast-mode beta header for Opus 5 and Opus 4.8. `default` sends `service_tier: "standard_only"`. |
| `gcp_vertex` (Claude) | `default`. `priority` only on Claude Fable 5.2 and Mythos 5.2. | `speed: "fast"` |
| `gcp_vertex` (Gemini) | `location: global`: `default`, `flex`, `priority`. `us` or `eu`: `default`, `priority`. Other locations: `default`. See [GCP Vertex AI](/providers/gcp-vertex/#service-tiers). | `X-Vertex-AI-LLM-Shared-Request-Type` header |
| `aws_bedrock` | `default`, `flex`, `priority` | `serviceTier` (Converse), `X-Amzn-Bedrock-Service-Tier` (InvokeModel), or `service_tier` (OpenAI-shaped API styles). Mantle Claude serves `default` only. |
| `github_copilot`, `typesafe`, Decisions | `default` | nothing |

A route serves a non-default tier only when its provider type can send the tier on the request's API and the gateway can price it. The gateway can price a tier when the provider reports the cost (OpenRouter), when the catalog or `pricing_override` has a rate for the tier, or when the route has no price at all. A request that no route can serve fails with 400.

Config loading checks a route's `service_tier` against this table. When no API the route serves can send the tier, the gateway doesn't start, and the error names the model, the route, the provider and the tier. For example, `flex` on `anthropic_compat`, `flex` on a Vertex Gemini route in `us`, and `ultrafast` on a direct OpenAI route with `capabilities.responses: false` all fail. `ultrafast` on a direct OpenAI route that also serves Responses loads, but Chat Completions and Messages requests don't use that route.

Embeddings, image generation, Decisions and batches run at the default tier, so they skip routes that force another tier. A model whose routes all force one can't serve them.

The model may not match the tier you choose. For example, OpenRouter's `claude-haiku-5.5` has no fast mode, so a fast request is served at standard speed. The request log shows the tier the caller requested and the tier the provider served. Usage is billed at the served tier.

The design and its trade-offs are in the [service tiers ADR](https://github.com/ahstn/oceans-llm/blob/main/docs/adr/2026-11-09-service-tiers.md).

## Model allowlists

`models[*].allowlist` limits which human users and teams may use a model. It's separate from API-key grants and from user, team, and service-account model restrictions.

```yaml
models:
  - id: finance-gpt-4o
    tags: [finance, fast]
    allowlist:
      users:
        - Analyst@Example.com
      teams:
        - Finance
    routes:
      - provider: openrouter
        upstream_model: openai/gpt-4o
```

Rules:

- `users` entries are trimmed and lowercased like config user emails. `teams` entries are normalised like config team keys. Duplicates collapse after normalisation.
- Unknown user and team refs are accepted, so a future user or team can match without a config change.
- `allowlist: {}`, empty `users` and `teams`, or refs that normalise to nothing fail config loading.
- Omitting `allowlist` means no model-level restriction. On reseed, omission also clears any allowlist stored earlier for that model.
- A user-owned API key may use the model when the user's normalised email or an effective team key is listed.
- A service-account-owned API key is always denied a model that has an allowlist, even when its team is listed.
- Aliases are separate models. An alias doesn't inherit its target's allowlist, and the target's allowlist doesn't apply to the alias.
- `tag:` selectors skip allowlisted models the caller can't use.

## Route fields

Each `models[*].routes[*]` entry sends the model to one provider.

<Aside type="note" title="Unknown route fields fail config loading">
Route entries reject unknown fields, including the fields inside `capabilities`, `compatibility` and its provider blocks. A misspelled key such as `service_teir` stops the gateway at startup.
</Aside>

| Field | Default | Notes |
| --- | --- | --- |
| `id` | none | Required on every route when the model has `routing`. Unique within the model. 1 to 128 ASCII letters, digits, periods, underscores, or hyphens. |
| `provider` | required | A `providers[*].id`. Unknown providers fail config loading. |
| `upstream_model` | required | Model name sent to the provider. `gcp_vertex` routes need `<publisher>/<model_id>`. |
| `priority` | `100` | Route priority. |
| `weight` | `1.0` | Weight for weighted selection. |
| `enabled` | `true` | Set `false` to keep the route but stop using it. |
| `context_window_tokens` | none | See [Route metadata overrides](#route-metadata-overrides). |
| `pricing_override` | none | See [Route metadata overrides](#route-metadata-overrides). |
| `service_tier` | none | Tier for every request on this route. See [Service tiers](#service-tiers). |
| `capabilities` | all unset | See [Route capabilities](#route-capabilities). |
| `compatibility` | none | See [Route compatibility](#route-compatibility). |
| `extra_headers` | `{}` | Headers added to upstream requests for this route. |
| `extra_body` | `{}` | Fields merged into the upstream request body. |

Keep route `id` stable when you change priority, weight, or YAML order. Changing `provider` or `upstream_model` creates a different internal route identity.

`extra_headers` is how you send provider headers such as `OpenAI-Project`. The gateway doesn't forward arbitrary caller headers to providers.

`extra_body` is for additive provider-specific fields. Don't use it for compatibility transforms. When a typed compatibility profile conflicts with `extra_body`, the profile wins.

Set a tier with the route's `service_tier`, not with `extra_body`, `extra_headers` or the provider's `default_headers`. Config loading fails when `extra_body` has `service_tier`, `serviceTier` or `speed`, or when `extra_headers` or `default_headers` has `X-Vertex-AI-LLM-Shared-Request-Type` or `X-Amzn-Bedrock-Service-Tier`.

An enabled route seeded by an earlier release can still hold one of these fields. The gateway then refuses to start, and the error names the model and the route. Seed the corrected config to replace the stored routes: restart the gateway with config seeding on (the default), or run `gateway seed-config`.

### Route metadata overrides

Route metadata is deployment policy, so it lives on each route.

```yaml
models:
  - id: contracted-model
    routes:
      - provider: private-provider
        upstream_model: upstream-model
        context_window_tokens: 128000
        pricing_override:
          input_usd_per_million_tokens: "1.2500"
          output_usd_per_million_tokens: "5.0000"
          cache_read_usd_per_million_tokens: "0.1250"
          cache_write_usd_per_million_tokens: "1.5000"
```

`context_window_tokens` is an optional positive integer. It can lower the route's effective context, but not raise it above a known catalog limit. Startup fails when the value is above a known catalog limit. When the catalog doesn't know the context, the value is accepted as admin policy. If a later catalog refresh reports a smaller limit, the gateway logs a warning and uses the catalog limit.

`pricing_override` is optional. When present:

- `input_usd_per_million_tokens` and `output_usd_per_million_tokens` are required.
- `cache_read_usd_per_million_tokens`, `cache_write_usd_per_million_tokens`, `cache_write_1h_usd_per_million_tokens`, and `image_output_usd_per_million_tokens` are optional. Omitted rates don't fall back to catalog rates. A cache bucket without a rate is charged from the input rate, and 1-hour cache writes default to twice the input rate. See [Cache-token accounting](/spend/pricing-and-accounting/#cache-token-accounting).
- The rates price the route's own tier: its `service_tier`, or `default` when it has none.
- `service_tiers` is an optional list of rates for the other tiers the route can bill. Each entry has `service_tier`, `input_usd_per_million_tokens`, `output_usd_per_million_tokens`, and optional `cache_read_usd_per_million_tokens`, `cache_write_usd_per_million_tokens`, and `cache_write_1h_usd_per_million_tokens`. A tier may appear once, and the route's own tier can't appear. A request billed at a tier with no entry is charged at the route's own rates as an estimate, with the reason `estimated_service_tier:<tier>`. Add an entry for each premium tier the route can serve, so its requests aren't billed at the lower rates.
- On a route with `service_tier: priority`, add a `default` entry to price requests that the provider serves at the default tier instead.
- Every rate is a quoted decimal string with at most four fractional digits. Zero is valid. Unquoted numbers, negative, malformed, and overflowing values fail config loading. Unknown fields are rejected.

```yaml
        pricing_override:
          input_usd_per_million_tokens: "1.2500"
          output_usd_per_million_tokens: "5.0000"
          service_tiers:
            - service_tier: priority
              input_usd_per_million_tokens: "2.5000"
              output_usd_per_million_tokens: "10.0000"
```

`image_output_usd_per_million_tokens` prices the image tokens a provider reports in `completion_tokens_details.image_tokens` or `output_tokens_details.image_tokens`. Other completion tokens use the output rate. A cost the provider reports in usage, such as OpenRouter's `usage.cost`, takes precedence over the whole override. See [Pricing catalog and accounting](/spend/pricing-and-accounting/).

### Route capabilities

`capabilities` holds flags that are `true`, `false`, or omitted:

- API families: `chat_completions`, `responses`, `embeddings`, `images`, `decisions`.
- Features: `stream`, `tools`, `vision`, `json_schema`, `developer_role`.

Omit a flag to let the gateway fill it in. Set it only to override. A route can narrow what the provider supports. It can't expand it. When nothing else sets a flag, `images` and `decisions` default to `false` and every other flag defaults to `true`. The order of sources and the catalog hint rules are described in [Model routing and APIs](/configuration/model-routing/).

Startup validation uses explicit flags, then compatibility inference, then defaults. It doesn't use catalog hints. An omitted flag never fails validation. An explicit flag that contradicts the route's compatibility fails startup.

Rules for specific flags:

- `decisions` works only on a `typesafe` provider, an `openai_compat` route with `compatibility.openai_compat.decisions_api: openai`, or an OpenRouter route with `compatibility.openrouter.api: decisions`. On these routes the gateway sets `decisions` to `true` and every other flag to `false`, so no `capabilities` block is needed. An explicit `decisions: false`, or `true` for any other flag, fails startup.
- `images` works only on `openai_compat` and `gcp_cloud_run_openai_compat` providers, and never on a Decisions route. Set `images: true` on routes that serve `POST /v1/images`.

## Route compatibility

Capabilities decide whether a route may serve a request. `compatibility` describes request and stream-shape transforms for the provider. Each profile belongs to one provider type.

| Profile | Valid on |
| --- | --- |
| `compatibility.openai_compat` | OpenAI-compatible routes |
| `compatibility.openrouter` | `openai_compat` providers whose `base_url` is HTTPS on `openrouter.ai` |
| `compatibility.aws_bedrock` | `aws_bedrock` providers (required) |
| `compatibility.github_copilot` | `github_copilot` providers |

For what each adapter does with these settings, see [Provider API compatibility](/reference/provider-api-compatibility/).

### OpenAI-compatible profile

| Field | Default | Accepted values |
| --- | --- | --- |
| `supports_store` | `true` | `true`, `false` |
| `max_tokens_field` | `max_completion_tokens` | `max_completion_tokens`, `max_tokens` |
| `developer_role` | `developer` | `developer`, `system` |
| `reasoning_effort` | `passthrough` | `passthrough`, `omit`, `reasoning_object` |
| `supports_stream_usage` | `true` | `true`, `false` |
| `empty_tools` | `preserve` | `preserve`, `omit`, `preserve_with_tool_history` |
| `decisions_api` | unset | `openai` |

`empty_tools` controls `tools: []` in Chat Completions and Responses requests:

- `preserve` keeps the empty array.
- `omit` removes it, for providers such as DashScope/Qwen that reject an empty array. Neutral `tool_choice` values (`auto`, `none`, `null`) are removed with it. `required` and named choices are rejected locally, because no tool can satisfy them.
- `preserve_with_tool_history` removes an empty array, but keeps it and `tool_choice` when the request has function-tool history. Some LiteLLM and Anthropic proxy routes need this.

`decisions_api: openai` sends the OpenAI Decisions format to `<base_url>/decisions`. It needs an `openai_compat` provider and can't be combined with `compatibility.openrouter`.

The other fields are Chat Completions transforms. `/v1/responses` is a separate API family and doesn't reuse them.

### OpenRouter profile

| Field | Default | Accepted values |
| --- | --- | --- |
| `api` | `open_ai_compat` | `open_ai_compat`, `decisions` |
| `provider.zdr` | unset | `true`, `false` |
| `provider.only` | `[]` | OpenRouter provider slugs |
| `provider.ignore` | `[]` | OpenRouter provider slugs |
| `provider.order` | `[]` | OpenRouter provider slugs in preferred order |
| `provider.preferred_max_latency` | unset | A positive number, or an object with at least one positive `p50`, `p75`, `p90`, `p99` (seconds) |
| `provider.max_price` | unset | An object with at least one non-negative `prompt`, `completion`, `request`, `image` |

Validation:

- Slug lists can't contain empty or duplicate entries, and a slug can't be in both `only` and `ignore`.
- With `api: open_ai_compat`, at least one `provider` field must be set. `api: decisions` may leave `provider` empty.
- A route can't set both `compatibility.openrouter` and `extra_body.provider`.
- Unknown fields are rejected.

### AWS Bedrock route compatibility

Every `aws_bedrock` route must set `compatibility.aws_bedrock.api_style`.

| Field | Notes |
| --- | --- |
| `api_style` | Required. Runtime styles need `endpoint_kind: bedrock_runtime`. Mantle styles need `bedrock_mantle`. |
| `openai_base_path` | Required for OpenAI-shaped styles (`runtime_openai_chat`, `mantle_openai_chat`, `mantle_openai_responses`), for example `/openai/v1`. Not allowed on other styles. |
| `supports_strict_tools` | Optional, `runtime_converse` only. |

The gateway infers these capabilities from `api_style`, so a Bedrock route needs no `capabilities` block for them:

| `api_style` | Inferred |
| --- | --- |
| `runtime_converse`, `runtime_openai_chat`, `mantle_openai_chat`, `mantle_anthropic_messages` | `chat_completions` and `stream` on. `responses`, `json_schema`, `embeddings`, `images`, `decisions` off. |
| `runtime_anthropic_invoke` | `chat_completions` on. `responses`, `stream`, `json_schema`, `embeddings`, `images`, `decisions` off. |
| `mantle_openai_responses` | `responses` and `stream` on. `chat_completions`, `embeddings`, `images`, `decisions` off. |

`tools` and `vision` (and `json_schema` on `mantle_openai_responses`) depend on the model. Catalog hints fill them when the catalog knows the model. Otherwise they default to `true`. Set them to `false` when the model lacks them. Startup rejects explicit flags that conflict with `api_style`, such as `stream: true` on `runtime_anthropic_invoke` or `responses: true` on any style other than `mantle_openai_responses`. It doesn't check live model support.

When `supports_strict_tools` is unset, `runtime_converse` routes infer it from transparent upstream model IDs, and omit `strict` for Claude Opus 4.7 and 4.8. Set it to `false` for opaque application inference profile IDs or ARNs backed by those models. An explicit value overrides inference.

### GitHub Copilot route compatibility

Copilot route support is fail-closed. Copy each value from a current `/models` response for the exact `upstream_model`. The [installation-token canary](/providers/github-copilot/#run-the-installation-token-canary) produces the projection you need.

| Field | Default | Notes |
| --- | --- | --- |
| `chat_api` | unset | `chat_completions` only when `supported_endpoints` has `/chat/completions`. `anthropic_messages` only when it has `/v1/messages`. Leave unset for Responses-only or embeddings-only routes. |
| `supports_responses` | `false` | |
| `supports_embeddings` | `false` | |
| `upstream_supports.streaming` | `false` | |
| `upstream_supports.tool_calls` | `false` | |
| `upstream_supports.vision` | `false` | |
| `upstream_supports.structured_outputs` | `false` | |

Unknown fields are rejected, and the profile is valid only on a `github_copilot` provider.

The gateway sets every capability flag from this evidence, so a Copilot route needs no `capabilities` block. Use `capabilities` only to turn off a feature the evidence declares. A flag can't enable support the evidence doesn't declare. `developer_role` and `images` are always off. `json_schema` is on only with `structured_outputs` and either `supports_responses` or `chat_api: chat_completions`.

```yaml
models:
  - id: copilot-chat
    routes:
      - provider: copilot-org
        upstream_model: <exact-model-id-from-canary>
        compatibility:
          github_copilot:
            chat_api: chat_completions
            supports_responses: false
            supports_embeddings: false
            upstream_supports:
              streaming: true
              tool_calls: true
              vision: true
              structured_outputs: false
```

## Route examples

OpenAI direct routes need no compatibility overrides:

```yaml
models:
  - id: openai-direct
    routes:
      - provider: openai-prod
        upstream_model: gpt-5
```

OpenAI-compatible aggregator routes declare known Chat Completions quirks:

```yaml
models:
  - id: openrouter-fast
    routes:
      - provider: openrouter
        upstream_model: openai/gpt-4o-mini
        compatibility:
          openai_compat:
            supports_store: false
            max_tokens_field: max_tokens
            developer_role: system
            reasoning_effort: omit
            empty_tools: omit
```

Streaming Chat Completions routes request usage by default. Set `supports_stream_usage: false` only for an upstream that rejects `stream_options`. Usage on those streams then depends on the provider sending it unasked.

OpenRouter routes can set upstream provider policy:

```yaml
models:
  - id: openrouter-fast-zdr
    routes:
      - provider: openrouter
        upstream_model: openai/gpt-4o-mini
        compatibility:
          openrouter:
            provider:
              zdr: true
              only: [openai, anthropic]
              ignore: [deepinfra]
              order: [openai, anthropic]
              preferred_max_latency:
                p90: 2.5
              max_price:
                prompt: 1.0
                completion: 2.0
```

An OpenRouter Decisions route needs no `capabilities` block:

```yaml
models:
  - id: jev
    routes:
      - provider: openrouter
        upstream_model: typesafe/jev-1.13
        compatibility:
          openrouter:
            api: decisions
```

Vertex routes use a publisher-qualified upstream model. Vertex text embeddings are configured as embedding-only routes for `google/gemini-embedding-001`, `google/gemini-embedding-2`, `google/text-embedding-005`, or `google/text-multilingual-embedding-002`. Flags left unset default to `true` unless the catalog says otherwise, so disable API families the route doesn't serve:

```yaml
models:
  - id: gemini-fast
    routes:
      - provider: vertex-adc
```

An OpenAI Decisions provider and route. `decisions_api: openai` turns `decisions` on and every other flag off, so no `capabilities` block is needed. The example rates are illustrative: set OpenAI's published input and cached-input rates. Decisions pricing is input-only, so output is `"0"`:

```yaml
providers:
  - id: openai-prod
    type: openai_compat
    base_url: https://api.openai.com/v1
    pricing_provider_id: openai
    auth:
      kind: bearer
      token: env.OPENAI_API_KEY

models:
  - id: luna
    routes:
      - provider: openai-prod
        upstream_model: gpt-6-luna
        compatibility:
          openai_compat:
            decisions_api: openai
        pricing_override:
          # Example rates: set OpenAI's published input and cached-input rates.
          input_usd_per_million_tokens: "1.2500"
          cache_read_usd_per_million_tokens: "0.1250"
          output_usd_per_million_tokens: "0"
```
