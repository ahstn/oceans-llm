# ADR CLI binary distribution with cargo-dist

- Date: 2026-10-05
- Status: Accepted
- Supersedes: GitHub release creation and distribution workflow ownership in [the release versioning ADR](2026-03-06-release-versioning-and-ghcr-publishing.md).

## Context

The authenticated Skills feature added an `oceans` executable in the `oceans-cli` package. Maintainers need prebuilt binaries on GitHub Releases. The existing release command already uses Cocogitto, cargo-release, and git-cliff to prepare a product version, but it publishes the GitHub release before CI finishes distributing images and the Helm chart.

The repository keeps one product version and a deliberate release command. It does not publish internal crates to crates.io or require a release PR for each version.

## Decision

Use cargo-dist to build CLI archives, checksums, shell and PowerShell installers, and the generated GitHub release workflow. Keep Cocogitto as the version and tag owner, cargo-release as the Cargo version updater, and git-cliff as the changelog owner.

The local `mise run release` task prepares and pushes the release commit and tag. CI owns GitHub release creation. The release is created in cargo-dist's announce phase after CLI artifact checks, container publication, and Helm chart publication succeed.

The initial targets are Linux x86-64 and ARM64, macOS Intel and Apple Silicon, and Windows x86-64. Each target uses a native runner. Only `oceans-cli` is selected for distribution, and precise builds exclude the wider gateway workspace from CLI compilation.

## Implementation

- [dist-workspace.toml](../../dist-workspace.toml) owns targets, packaging settings, pinned Action commits, and custom job registration.
- [release.yml](../../.github/workflows/release.yml) is generated by the pinned cargo-dist version. Maintainers regenerate it through `mise run dist-generate` and check it through `mise run dist-check`.
- [release-cli-check.yml](../../.github/workflows/release-cli-check.yml) verifies checksums and runs the packaged executable. It also tests CLI and bundle behavior on each target operating system.
- [release-product.yml](../../.github/workflows/release-product.yml) retains the image and chart publication jobs as a reusable workflow. cargo-dist calls it before announce.
- [cog.toml](../../cog.toml) updates all Cargo versions and explicitly writes `CHANGELOG.md` before the version commit. Both release tools are declared in [mise.toml](../../mise.toml).

Pull requests build and check the distribution artifacts without publishing. The generated workflow remains unedited. Build setup installs the repository Rust toolchain through `mise`, and reusable job commands run through `mise`.

## Reasons and tradeoffs

cargo-dist supplies archive generation, installer generation, manifests, and distribution CI as one maintained tool. This reduces repository-owned packaging code and allows future distribution changes through configuration.

GitHub publication runs at the end because the current publish jobs do not need CLI download URLs. Adding Homebrew or npm publication requires a review of release timing, since those packages can depend on assets that are already hosted.

The completion gate does not make publication atomic across GitHub, GHCR, and Helm. Images and charts can remain available if a later job fails. Published tags and assets must not be replaced to recover a failed release.

The initial Linux builds use Ubuntu 22.04 and glibc. Maintainers must check linkage reports and runtime compatibility before promising an older Linux baseline or adding musl targets. Platform support is verified by CI, not inferred from target configuration alone.

## Follow up

Confirm the first hosted build for every configured target. Review the downloaded binaries, installer behavior, and provenance against the release runbook. Add signing or package manager publication only when there is a defined user requirement.
